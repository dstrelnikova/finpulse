# Требования к FinPulse

Статусы в документе: **AS-IS** — подтверждено кодом; **TARGET** — требуемое поведение; **GAP** — расхождение или технический долг. Связи с проверками приведены в [матрице трассируемости](traceability-matrix.md).

Значение типов требований и правила формулировки: [памятка системного аналитика](analysis-guide.md#4-требования).

## 1. Назначение системы

FinPulse — учебный веб-сервис для просмотра и анализа новостей российского финансового рынка, получения котировок выборки бумаг MOEX и диалога с AI-ассистентом. Результаты носят информационный характер и не являются инвестиционной рекомендацией.

## 2. Проблема

Финансовая информация распределена по нескольким источникам и требует времени на отбор и первичный анализ. Сервис собирает RSS-материалы, приводит анализ к единому формату и показывает его вместе с рыночными данными.

## 3. Цели

- предоставить публичную витрину актуальных русскоязычных финансовых новостей;
- выделять содержание, факты, риски и возможный рыночный сигнал;
- дать зарегистрированному пользователю профиль и контекстный AI-чат;
- сохранить воспроизводимый full-stack MVP с документированным API и данными.

## 4. Actors / пользователи

| Actor | Возможности |
|---|---|
| Гость | Публичные новости, карточка новости, выборка котировок MOEX, регистрация и вход |
| Пользователь | Возможности гостя, профиль, персональная лента, AI-чат и его история |
| Администратор | Возможности пользователя, список пользователей и назначение ролей |
| Внешние системы | RSS-источники, MOEX ISS, GigaChat API и локальный Ollama |

## 5. Scope

В scope входят React-клиент, FastAPI REST API, PostgreSQL, RSS-сбор, анализ новостей, GigaChat/Ollama, MOEX ISS, JWT/RBAC, Docker Compose и CI-проверки. Tauri является оболочкой существующего React-клиента.

## 6. Out of Scope

- торговые операции, брокерский счёт и управление деньгами;
- гарантированный прогноз цены и инвестиционные рекомендации;
- обучение собственной ML/LLM-модели;
- production deployment, Kubernetes и облачная инфраструктура;
- push-уведомления и биллинг;
- локальный каталог `mobile/`: он исключён из Git и не является поставляемой частью репозитория.

## 7. Основные пользовательские сценарии

Подробно: [Use Cases](use-cases.md). Ключевые сценарии — просмотр публичной новости, регистрация и вход, настройка профиля, диалог с AI и администрирование ролей.

## 8. Функциональные требования

| ID | Статус | Требование |
|---|---|---|
| FR-01 | AS-IS | По `GET /public/news` система должна возвращать не более запрошенного `limit` публичных русскоязычных новостей, прошедших фильтры качества; эффективный диапазон `limit` — 1–100. |
| FR-02 | AS-IS | По существующему числовому ID или slug система должна вернуть публичную новость в формате `NewsBlockOut`, а для отсутствующей новости — HTTP 404. |
| FR-03 | AS-IS | По `GET /public/moex/imoex/quotes` система должна вернуть 1–20 элементов выборки IMOEX; при недоступности MOEX ISS — тот же контракт с `fallback=true` и пустыми ценовыми значениями. |
| FR-04 | AS-IS | По валидному `POST /auth/register` система должна создать пользователя с уникальным email и хешем пароля; дублирующий email должен давать HTTP 400. |
| FR-05 | AS-IS | По корректным credentials система должна выдать пару access/refresh JWT, а по некорректным — HTTP 401 без токенов. |
| FR-06 | AS-IS | По валидному сохранённому refresh JWT система должна ротировать пару токенов; повторное использование заменённого токена должно давать HTTP 401. |
| FR-07 | AS-IS | По валидному `POST /auth/logout` система должна удалить сохранённый refresh token текущего пользователя. |
| FR-08 | AS-IS | Пользователь с правом `profile:update_own` должен изменять только свой профиль; тикеры нормализуются в верхний регистр и дедублируются, значения справочников валидируются. |
| FR-09 | AS-IS | Пользователь с правом `chat:use` должен отправлять в Ollama сообщение длиной 1–4000 символов и получать ответ; недоступность модели должна давать HTTP 503. |
| FR-10 | AS-IS | Успешный обмен чата должен сохраняться в default chat текущего пользователя. |
| FR-11 | AS-IS | Чтение истории должно возвращать 1–200 последних сообщений только default chat текущего пользователя. |
| FR-12 | AS-IS | Пользователь с permission `admin_users:list` должен получать фильтруемый, сортируемый и пагинированный список пользователей; остальным возвращается HTTP 403. |
| FR-13 | AS-IS | Пользователь с permission `admin_users:assign_role` должен заменять роли выбранного пользователя только значениями `user`, `pro`, `admin`; неизвестная роль/пользователь даёт HTTP 400. |
| FR-14 | AS-IS | Пользователь с правом `news:list` должен получать персональную RSS-ленту, построенную с учётом профиля и кэша; при отключённом или недоступном GigaChat применяется rules-based анализ. |
| FR-15 | AS-IS | По `GET /meta/options` система должна возвращать допустимые рынки, категории, горизонты, уровни опыта/риска и секторы, используемые клиентом для ввода профиля. |

## 9. Нефункциональные требования

| ID | Статус | Проверяемое требование |
|---|---|---|
| NFR-01 | AS-IS | Секреты и параметры окружения должны поступать через environment variables; реальные `.env` не должны отслеживаться Git. |
| NFR-02 | AS-IS | Невалидные тела и объявленные query-параметры FastAPI должны отклоняться HTTP 422 до выполнения бизнес-логики. |
| NFR-03 | AS-IS | Недоступность RSS, GigaChat или MOEX не должна приводить к необработанному HTTP 500 в публичной ленте/котировках; используются пропуск источника, rules fallback или fallback-ответ. |
| NFR-04 | AS-IS | PostgreSQL должен обеспечивать уникальность `users.email`, `news.url`, комбинаций кэша и RBAC, а также каскадное удаление зависимых chat/RBAC-записей. |
| NFR-05 | AS-IS | Каждый push в `main` и каждый pull request должны запускать backend tests, frontend typecheck/tests и frontend build в GitHub Actions. |
| NFR-06 | AS-IS | `/healthz` должен отвечать HTTP 200 без обращения к БД, а `/readyz` — HTTP 200 только при успешном `SELECT 1`, иначе HTTP 503. |

## 10. Системные правила

- рынок профиля фиксирован значением `RU`;
- новая учётная запись получает роль `user` при startup seed;
- `ADMIN_EMAIL`, если пользователь существует, получает только роль `admin` при startup seed;
- публичная лента использует stale-while-revalidate и cooldown обновления;
- публичный API не позволяет принудительно запускать обновление ленты; обновление выполняет внутренний scheduler;
- `chat_id` присутствует в клиентском контракте, но AS-IS backend использует только default chat пользователя.

## 11. Ограничения и GAP

- **GAP-01:** нет Alembic/версируемых миграций; таблицы создаются через `Base.metadata.create_all`, а `subscription_tier` добавляется SQL-командой при старте и отсутствует в ORM-модели.
- **GAP-02:** refresh token хранится в БД в исходном виде, а не в виде хеша.
- **GAP-03:** rate limit аутентификации хранится в памяти процесса и не масштабируется на несколько экземпляров.
- **GAP-04:** автоматический deployment отсутствует; workflow реализует только CI.
- **GAP-05:** branch protection и обязательные status checks не подтверждены; наличие workflow само по себе не запрещает merge при FAIL.
- **GAP-06:** persistent Docker volume содержит legacy-таблицу `files`, которой нет в текущих ORM-моделях и API.
- **GAP-07:** `npm audit` после безопасного обновления зависимостей показывает 2 moderate проблемы React Router; исправление требует отдельного перехода на major version 7.

## 12. Внешние зависимости

PostgreSQL 16; RSS Банка России, Московской биржи, Интерфакса и Коммерсанта; MOEX ISS; GigaChat OAuth/chat completions; Ollama Generate API; Docker images с Docker Hub. Поведение интеграций подробно описано в [архитектуре](architecture.md) и [API](api.md).
