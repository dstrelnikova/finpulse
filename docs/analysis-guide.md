# Памятка системного аналитика по FinPulse

Короткая памятка по артефактам проекта. Подробные примеры находятся в соседних файлах `docs/`.

## 1. Как связаны артефакты

```text
Потребность пользователя
→ Use Case
→ Требование
→ Критерии приёмки
→ Реализация
→ Тест-кейс
→ Результат проверки
```

Пример FinPulse:

```text
Пользователь хочет получить ответ на финансовый вопрос
→ UC-04 «Диалог с AI-ассистентом»
→ FR-09 «Отправка сообщения в чат»
→ AC-10 и AC-11
→ POST /chat/send, FastAPI, Ollama
→ TC-07 и TC-08
```

## 2. Основные термины

| Термин | Простое объяснение |
|---|---|
| Stakeholder | Заинтересованная сторона: влияет на систему или зависит от результата |
| Actor | Роль человека или внешней системы, которая взаимодействует с FinPulse |
| Goal | Результат, который хочет получить actor |
| Use Case (`UC`) | Описание достижения одной цели: нормальный путь, альтернативы и ошибки |
| Functional Requirement (`FR`) | Что система должна делать |
| Non-Functional Requirement (`NFR`) | С каким качеством или при каких ограничениях должна работать система |
| Acceptance Criteria (`AC`) | По каким признакам требование считается выполненным |
| Test Case (`TC`) | Как именно проверить требование |
| Матрица трассируемости | Таблица связей между UC, требованиями, AC и TC |

Контекст и actors FinPulse описаны в [context.md](context.md).

## 3. Use Case

Use Case описывает, как actor достигает конкретной цели.

### Шаблон

```markdown
## UC-NN — Название

**Actor:** кто выполняет сценарий
**Goal:** какой результат ему нужен
**Preconditions:** что должно быть выполнено до начала
**Trigger:** что запускает сценарий
**Postconditions:** что изменилось после завершения

**Main Flow:**
1. Действие пользователя.
2. Ответ системы.

**Alternative Flows:**
- Другой допустимый путь к результату.

**Exceptions:**
- Ошибка или ситуация, когда результат не получен.
```

Важно:

- `Main Flow` — обычный успешный путь;
- `Alternative Flow` — другой допустимый путь;
- `Exception` — ошибка;
- один Use Case описывает одну пользовательскую цель.

Примеры: [use-cases.md](use-cases.md).

## 4. Требования

| Вид | Вопрос | Пример |
|---|---|---|
| Business Requirement | Зачем это нужно проекту? | Сократить время первичного анализа новостей |
| User Requirement | Что нужно пользователю? | Получить краткий анализ новости |
| Functional Requirement | Что должна делать система? | Вернуть новость по ID |
| Non-Functional Requirement | Как должна работать система? | Не раскрывать секреты в Git |
| Business Rule | Какое правило действует в продукте? | Рынок профиля — только `RU` |
| Constraint | Что ограничивает решение? | Данные хранятся в PostgreSQL |

Минимальные поля требования:

- `ID` — уникальный номер, например `FR-09`;
- `Status` — `AS-IS`, `TARGET` или `GAP`;
- `Description` — что должна делать система;
- `Source` — откуда появилось требование;
- `Priority` — насколько оно важно;
- `Acceptance Criteria` — как будет приниматься.

Хорошее требование описывает одну обязанность, понятно читается, не противоречит другим требованиям и может быть проверено.

Плохо:

> AI должен быстро давать хорошие ответы.

Слова «быстро» и «хорошие» нельзя объективно проверить. Нужны конкретные условия и ожидаемый результат.

Примеры: [requirements.md](requirements.md).

## 5. Критерии приёмки

Критерии приёмки отвечают на вопрос: как понять, что требование выполнено?

```text
Given — исходные условия
When — действие или событие
Then — ожидаемый результат
```

Пример:

```text
Given пользователь имеет право chat:use
When он отправляет сообщение длиной 1–4000 символов
Then backend возвращает HTTP 200 и непустой answer
```

Критерии должны быть конкретными и проверяемыми. Для одной функции могут понадобиться критерии успешного поведения, ошибок и граничных значений.

Примеры: [acceptance-criteria.md](acceptance-criteria.md).

## 6. Тест-кейс

Test Case — конкретная процедура проверки.

```markdown
## TC-NN — Название

**Related requirement:** FR-NN
**Related acceptance criterion:** AC-NN
**Preconditions:** состояние до проверки
**Steps:** действия проверяющего
**Expected Result:** ожидаемый результат
**Actual Result:** фактический результат
**Status:** PASS / FAIL / BLOCKED / NOT RUN
```

Виды проверок:

- `positive` — корректные данные и успешный путь;
- `negative` — неправильные данные или ошибка;
- `boundary` — значения на границе и рядом с ней.

Для диапазона 1–4000 символов проверяются `0`, `1`, `4000` и `4001`.

Статусы:

- `PASS` — выполнено, результат совпал с ожидаемым;
- `FAIL` — выполнено, результат не совпал;
- `BLOCKED` — выполнить мешает зафиксированное препятствие;
- `NOT RUN` — ещё не выполнялось.

Нельзя ставить `PASS` только потому, что тест написан.

Примеры: [test-cases.md](test-cases.md).

## 7. Матрица трассируемости

Матрица показывает, какой сценарий и какие проверки относятся к каждому требованию.

| Requirement | Use Case | Acceptance Criteria | Test Cases |
|---|---|---|---|
| FR-09 | UC-04 | AC-10, AC-11 | TC-07, TC-08 |

Строка читается так: `FR-09` относится к `UC-04`, принимается по `AC-10/AC-11` и проверяется `TC-07/TC-08`.

Матрицу начинают заполнять после появления первых требований. Затем добавляют AC и TC. При изменении требования проверяют всю связанную цепочку и обновляют затронутые документы.

Пример изменения лимита сообщения:

```text
FR-09
→ UC-04
→ AC-10, AC-11
→ POST /chat/send
→ схема запроса
→ TC-07
```

Реальная матрица: [traceability-matrix.md](traceability-matrix.md).

## 8. Что проверить перед review

- У требования есть ID и понятный смысл.
- `AS-IS` отделён от `TARGET` и `GAP`.
- Понятно, в каком Use Case используется требование.
- Есть проверяемые критерии приёмки.
- Есть тест-кейс либо явно указан `NOT RUN`.
- Матрица соответствует требованиям, AC и тестам.
- После изменения обновлены все затронутые документы.
