# Use Cases

Все сценарии описывают **AS-IS**, кроме явно отмеченных GAP. Требования: [requirements.md](requirements.md).

## UC-01 — Просмотр публичной новости

**Actor:** Гость или пользователь
**Goal:** Получить отобранную финансовую новость и её анализ.
**Trigger:** Actor открывает публичную ленту.

**Preconditions:** Backend и PostgreSQL доступны.
**Postconditions:** Лента показана; при обновлении новые уникальные материалы сохранены в `news`.

**Main Flow:**

1. React отправляет `GET /public/news?limit=N`.
2. FastAPI читает публичные записи из PostgreSQL.
3. Backend фильтрует язык, возраст и качество анализа.
4. React показывает карточки; переход по slug вызывает `GET /public/news/slug/{slug}`.

**Alternative Flows:**

- A1. При пустой БД backend синхронно получает RSS, анализирует и сохраняет материалы.
- A2. При непустой БД данные возвращаются сразу, а обновление запускается в фоне.
- A3. При недоступном GigaChat применяется rules-based анализ.

**Exceptions:**

- E1. Неизвестный slug даёт HTTP 404.
- E2. Недоступный отдельный RSS-источник журналируется и пропускается.

## UC-02 — Регистрация и вход

**Actor:** Гость
**Goal:** Создать учётную запись и получить защищённый доступ.
**Trigger:** Actor отправляет форму регистрации, затем форму входа.

**Preconditions:** Backend и PostgreSQL доступны.
**Postconditions:** Пользователь сохранён; после входа refresh token сохранён, клиент хранит пару JWT.

**Main Flow:**

1. React отправляет `POST /auth/register`.
2. Pydantic проверяет имя, email и пароль; backend хеширует пароль и создаёт пользователя.
3. Actor отправляет `POST /auth/login`.
4. Backend проверяет пароль, создаёт access/refresh JWT и возвращает их.
5. React вызывает `/me` с Bearer access token и строит доступное меню по ролям/permissions.

**Alternative Flows:**

- A1. После HTTP 401 API-клиент один раз вызывает `/auth/refresh`, сохраняет новую пару и повторяет исходный запрос.

**Exceptions:**

- E1. Дублирующий email даёт HTTP 400.
- E2. Невалидный ввод даёт HTTP 422.
- E3. Неверный пароль или refresh token даёт HTTP 401.
- E4. Более 20 попыток на IP+ключ за 5 минут дают HTTP 429 в рамках одного процесса.

## UC-03 — Настройка профиля

**Actor:** Аутентифицированный пользователь
**Goal:** Задать контекст персонализации.
**Trigger:** Actor сохраняет форму профиля.

**Preconditions:** Валидный access JWT и permissions `profile:read_own`, `profile:update_own`.
**Postconditions:** Поля профиля пользователя обновлены в `users`.

**Main Flow:**

1. React получает справочники через `/meta/options` и профиль через `GET /profile`.
2. Actor выбирает горизонт, опыт, риск, секторы и вводит тикеры.
3. React отправляет `PATCH /profile`.
4. Backend валидирует и нормализует значения, затем обновляет пользователя.
5. React показывает сохранённый профиль.

**Alternative Flows:** A1. Частичный PATCH меняет только переданные поля.
**Exceptions:** E1. Недопустимый сектор/тикер даёт HTTP 422; E2. недостаток прав — HTTP 403.

## UC-04 — Диалог с AI-ассистентом

**Actor:** Пользователь с правом `chat:use`
**Goal:** Получить информационное объяснение с учётом профиля и истории.
**Trigger:** Actor отправляет сообщение в чат.

**Preconditions:** Валидный access JWT; Ollama и модель доступны.
**Postconditions:** Сообщение пользователя и корректный ответ сохранены в `chat_messages` default-сессии.

**Main Flow:**

1. React отправляет `POST /chat/send`.
2. Backend находит/создаёт default chat и читает последние сообщения.
3. Use case строит prompt из вопроса, профиля и истории.
4. Ollama возвращает ответ; backend проверяет его правилами качества.
5. Backend сохраняет обмен и возвращает `{answer, chat_id}`.

**Alternative Flows:** A1. При некачественном первом ответе use case может выполнить корректирующий запрос.
**Exceptions:** E1. Пустое/слишком длинное сообщение — HTTP 422; E2. недоступная модель — HTTP 503; E3. недостаток прав — HTTP 403.

## UC-05 — Управление ролями

**Actor:** Администратор
**Goal:** Просмотреть пользователей и изменить роли выбранного пользователя.
**Trigger:** Actor открывает `/admin/users`.

**Preconditions:** Валидный access JWT и admin permissions.
**Postconditions:** Набор связей `user_roles` атомарно заменён при успешном запросе.

**Main Flow:**

1. React вызывает `GET /admin/users` с фильтрами, сортировкой и пагинацией.
2. Backend проверяет permission и возвращает страницу пользователей.
3. Actor выбирает роли; React вызывает `PUT /admin/users/{id}/roles`.
4. Backend проверяет существование пользователя и ролей, заменяет связи и возвращает итоговый набор.

**Alternative Flows:** A1. Список фильтруется по имени/email или роли.
**Exceptions:** E1. Неадминистратор получает HTTP 403; E2. неизвестная роль/пользователь — HTTP 400.
